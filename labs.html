Hilo conductor

Cada lab prepara el siguiente y expone un problema que el posterior resuelve:

  1. Lab 01 construye un GC que razona sobre alcanzabilidad (y por eso recolecta ciclos, cosa que el conteo de referencias no puede). Pero marca en un solo hilo.
  2. Lab 02 aísla el patrón de sincronización (mutex + variables de condición) sobre una cola de trabajo, y mide la contención cuando varios hilos comparten estado.
  3. Lab 03 une ambos: reparte el marcado del GC entre N hilos. Resuelve la corrección (marcar cada objeto exactamente una vez + detectar terminación) y, honestamente, mide por qué un diseño ingenuo no escala.
Metodología. Cada lab sigue la misma estructura: objetivo técnico · información disponible · herramientas · procedimiento · resultados verificables · conclusiones y limitaciones. Toda afirmación de corrección está respaldada por un assert, una comparación con una referencia, o un sanitizer (AddressSanitizer / ThreadSanitizer).

Alcance

Estudio de ingeniería sobre componentes de código abierto (WebKit / JavaScriptCore) y desarrollo de herramientas educativas con código propio. Los labs no dependen de ningún binario cerrado ni de ningún dispositivo: se compilan y verifican en cualquier Linux con gcc/clang.

Lab 01 — Recolector mark-and-sweep

Reproduce el mecanismo central de gestión de memoria automática: heap de objetos, conjunto de raíces, marcado por alcanzabilidad y barrido de lo inalcanzable.

Simulador interactivo

El grafo tiene dos raíces (R1, R2). Pulsa Marcar para recorrer el grafo desde las raíces; luego Barrer para liberar lo que quedó sin marcar. Observa dos cosas: el ciclo A↔B es alcanzable y sobrevive; el ciclo huérfano X↔Y se recolecta (algo imposible con conteo de referencias), igual que el objeto suelto G.

Cómo funciona

Fase de marcado

Recorrido recursivo del grafo desde las raíces. El bit marked corta los ciclos: si un objeto ya está marcado, no se vuelve a visitar.

static void mark(Object *obj) {
  if (obj == NULL) return;
  if (obj->marked) return;  // corta ciclos
  obj->marked = 1;
  if (obj->type == OBJ_PAIR) {
    mark(obj->head);
    mark(obj->tail);
  }
}

Fase de barrido

Recorre la lista global de objetos; libera los no marcados y limpia la marca de los vivos para el siguiente ciclo.

static void sweep(VM *vm) {
  Object **o = &vm->first;
  while (*o) {
    if (!(*o)->marked) {
      Object *dead = *o;
      *o = dead->next;
      free(dead);
    } else {
      (*o)->marked = 0;   // reset
      o = &(*o)->next;
    }
  }
}

Resultados verificables

El programa termina con assert en tres escenarios; falla ruidosamente si una invariante se rompe.

1 · Inalcanzablesobjetos sin referencia se liberanfreed = 2
2 · Raíceslo alcanzable sobrevive a 101 asignacionesvivos = 1
3 · Ciclo huérfanoun ciclo sin raíz se recolecta enterovivos = 0
AddressSanitizer + UBSan: ejecución sin errores de memoria ni fugas.
Limitaciones frente a un GC de producción (JSC Riptide)
  • Es stop-the-world; Riptide marca concurrentemente con la ejecución.
  • No es generacional (JSC separa objetos jóvenes/viejos).
  • Marcado recursivo → riesgo de desbordar la pila; los reales usan una mark stack explícita.
  • Sin compactación ni manejo de fragmentación.

Lab 02 — Productor/consumidor con buffer acotado

El patrón de sincronización más común en runtimes concurrentes: una cola de trabajo de capacidad fija que coordina varios hilos con un mutex y dos variables de condición.

Buffer acotado en acción

Capacidad fija de 16 celdas (como en el lab). El productor (puntero tail) escribe; el consumidor (puntero head) lee. Cuando el buffer se llena, el productor espera; cuando se vacía, el consumidor espera. Ajusta las velocidades y observa cómo se llena o se drena.

Las reglas de oro

while, nunca if

Al despertar hay que re-verificar la condición: puede haber despertares espurios, y con varios hilos otro pudo consumir el hueco antes.

while (q->count == BUFFER_CAP)
  pthread_cond_wait(&q->not_full, &q->lock);
// ...producir...
pthread_cond_signal(&q->not_empty);

Terminación limpia

El último productor en acabar despierta a todos los consumidores con broadcast, para que ninguno quede bloqueado esperando datos que no llegarán.

q->producers_remaining--;
if (q->producers_remaining == 0)
  pthread_cond_broadcast(&q->not_empty);

Resultados verificables

Invariante de conservación: la suma y el conteo de lo consumido deben coincidir exactamente con lo producido, comprobado por tres vías independientes. Probado en cargas simétricas y asimétricas:

Lab 03 — Marcado paralelo del GC

Cruce de los labs 01 y 02: la fase de marcado se reparte entre N hilos que drenan una mark stack compartida. Es el núcleo de un GC concurrente real.

Problema 1 — Marcar exactamente una vez

Si dos hilos descubren el mismo objeto a la vez, ambos podrían intentar empujarlo a la pila (y escanearlo dos veces). La solución es un bit de marca atómico: gana quien pase la marca de 0 a 1 con atomic_exchange, y solo ese hilo lo empuja.

Objeto O sin marcar. Dos hilos ejecutan atomic_exchange(&O->marked, 1) a la vez. Pulsa para simular la carrera:

La operación atómica garantiza que solo un hilo "gana" y empuja el objeto.
unsigned char prev = atomic_exchange(&c->marked, 1);
if (prev == 0) winners[nw++] = c;   // gane yo: empujo el hijo

Problema 2 — Detección de terminación

Un hilo que ve la pila vacía no puede salir: otro hilo activo podría estar a punto de empujar hijos. Se cuenta cuántos hilos están ociosos. La clave sutil:

Un hilo que sacó un objeto de la pila lo tiene «en la mano» y no se cuenta como ocioso. Así su trabajo pendiente impide declarar el fin. Solo cuando idle == nworkers con la pila vacía no hay trabajo en vuelo → done + broadcast. 
ms->idle++;
if (ms->idle == ms->nworkers) {   // todos ociosos + pila vacia = fin
  ms->done = true;
  pthread_cond_broadcast(&ms->cond);
  return NULL;
}
while (ms->size == 0 && !ms->done)
  pthread_cond_wait(&ms->cond, &ms->lock);

Resultados: correcto, pero NO escala

La corrección es sólida: el conjunto marcado en paralelo es idéntico al de un marcado secuencial de referencia (DFS) para 1, 2, 4 y 8 hilos; escaneados == alcanzables; el barrido libera exactamente los inalcanzables; y TSan no reporta carreras.

Pero el tiempo medido (200 000 objetos, 150 436 alcanzables) revela lo contrario de lo esperado:

hilosescaneadoscorrectotiempo
1150 436✓13.4 ms
2150 436✓58.5 ms
4150 436✓66.2 ms
8150 436✓64.4 ms
Hallazgo honesto. Más hilos = más lento. No es un fallo de corrección: es el resultado central del lab. Causa: un mutex único global serializa todos los push/pop, y el trabajo por objeto (escanear ≤ 6 punteros) es minúsculo frente al coste de sincronizar. La contención domina. El broadcast en cada push además genera despertares innecesarios (thundering herd).

Por eso los GC de producción no usan una pila global con lock, sino una mark stack por hilo con work-stealing (robo de trabajo), que minimiza la sincronización al caso de robo. Ese es el Lab 04 natural.

Cómo ejecutar

Cada lab es autónomo: cd a su carpeta y usa make. Requiere gcc o clang y make (y -lpthread, ya incluido en los labs 02/03).

Lab 01 — GC

cd lab01-gc
make run        # compila y ejecuta los 3 escenarios con asserts
make asan       # recompila con AddressSanitizer + UBSan

Lab 02 — Concurrencia

cd lab02-concurrency
make run              # 4 prod / 4 cons / 100k items
make stress          # cargas asimetricas 1x8, 8x1, 8x8
make tsan            # ThreadSanitizer: verifica ausencia de races
./conc 2 3 10000     # parametros propios: n_prod n_cons items/prod

Lab 03 — GC paralelo

cd lab03-parallel-gc
make run                 # marca con 1,2,4,8 hilos y verifica vs. referencia
make tsan                # ThreadSanitizer (grafo menor)
./pgc 500000 400000      # n objetos, region alcanzable-elegible
Verificación en dos niveles. funcional — assert / comparación con una referencia / invariante de conservación. memoria y concurrencia — AddressSanitizer (fugas, accesos inválidos) y ThreadSanitizer (condiciones de carrera). Un lab solo se considera correcto cuando pasa ambos.
